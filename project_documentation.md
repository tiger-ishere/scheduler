# Smart Transport Optimizer: Project Documentation

This document provides a comprehensive technical breakdown of the Smart Transport Optimizer project. It is designed to provide all the necessary details required to create system architectures, data flow diagrams, sequence diagrams, and class diagrams.

---

## 1. System Overview & Technology Stack

The project is a web-based scheduling and route optimization engine for a fleet of transport vehicles (e.g., buses). It calculates the optimal way to deploy vehicles to reach specific stops at specific target times, minimizing lateness and optimizing fleet utilization.

### Technology Stack
*   **Frontend Client:** React.js powered by Vite (JavaScript).
*   **Mapping Library (Frontend):** Leaflet & React-Leaflet for plotting routes and stops.
*   **Backend Server:** Python 3 with FastAPI.
*   **Database:** MongoDB (MongoDB Atlas Cloud). Database access managed via `motor` (Async MongoDB Driver).
*   **Routing API:** OpenRouteService (ORS) API for real-world distances and driving durations.
*   **Mathematical Solver Engine:** Google OR-Tools (Constraint Programming & Integer Linear Programming).

---

## 2. Core Modules & Responsibilities (Backend)

The backend is modularized into distinct files, each handling a specific layer of the application.

1.  **`main.py` (The API Gateway / Orchestrator)**
    *   Initializes the FastAPI application.
    *   Defines endpoints (`/optimize`, `/generate-frequency`, `/save-schedule`, `/login`, `/register`).
    *   Receives HTTP requests from the React frontend, coordinates the routing, fetches geographical paths (polylines) from ORS, formats the results, and returns the JSON payload back to the client.
2.  **`scheduler.py` (The Heavy Computing Engine)**
    *   Builds the routing Data Model based on incoming stop coordinates and time windows.
    *   Queries OpenRouteService to build a *Time/Distance Matrix* (how long it takes to get from every stop to every other stop). Contains a Haversine geometric fallback if the API fails.
    *   Runs the `Google OR-Tools` solver to calculate the Vehicle Routing Problem (VRPTW).
    *   Balances "Punctuality" vs. "Fleet Utilization" via dynamic cost/penalty parameters.
3.  **`optimizer.py` (The Evaluator)**
    *   Evaluates the final schedule generated by `scheduler.py`.
    *   Iterates through stops to calculate exactly how early or late a bus is arriving compared to the user's requested target time.
    *   Generates a final `score` and `penalty` metric.
4.  **`models.py` (Data Structures)**
    *   Uses `Pydantic` to enforce strict schema definitions for inputs and outputs.
    *   Defines models like `ScheduleRequest`, `LocationNode`, `UserCreate`, `UserLogin`, etc.
5.  **`database.py` (Persistence Layer)**
    *   Manages the asynchronous connection pool to MongoDB Atlas via the `.env` connection string.
    *   Exposes `users_collection` and `schedules_collection` for read/write queries.
6.  **`auth.py` (Security Layer)**
    *   Manages user authentication via JSON Web Tokens (JWT).
    *   Hashes passwords securely and handles token expirations.

## 3. Detailed Data Flow & Working Mechanism

Below is the step-by-step data flow when a user requests an optimized schedule from the frontend. This flow is ideal for creating a **Sequence Diagram**.

### Step 1: Client Request Formulation
*   The user drops pins on the map in the React frontend, setting a **Target Arrival Time** and **Service Time** (wait time) for each stop.
*   The user selects an optimization mode: **Strict Punctuality** or **Maximize Fleet Utilization**.
*   The React app compiles this into a JSON array of `LocationNode` objects and sends an HTTP POST request to the backend's `/optimize` endpoint.

### Step 2: Input Validation (`main.py` & `models.py`)
*   FastAPI routes the request to the `optimize_schedule` function.
*   `models.py` validates the payload. If coordinates or time limits are missing/malformed, it immediately returns an HTTP 422 error.

### Step 3: Matrix Generation (`scheduler.py` & OpenRouteService)
*   `scheduler.py` extracts all coordinates and makes an external API call to OpenRouteService (`distance_matrix`).
*   It receives the real-world driving duration (in seconds) between all points.
*   It converts these seconds to minutes (multiplying by a factor of 1.5 to account for heavy vehicle physics) to build a mathematical 2D array known as the **Time Matrix**.

### Step 4: The Optimization Solver (`scheduler.py` & Google OR-Tools)
*   The system initializes the `pywrapcp` Routing Index Manager.
*   **Dummy Node Injection:** It injects a "Dummy Start Node" (Node 0). All vehicles start here.
*   **Constraint Setup:** It registers transit callbacks to tell the engine how long travel takes. It applies "Soft Time Windows" to each stop based on the user's requested target time.
*   **Penalty Logic:**
    *   *If optimized for Punctuality:* The solver assigns a high penalty (50 points/min) for being late, and a low cost (200 points) to deploy a new bus. This forces the system to use more buses to ensure everyone is on time.
    *   *If optimized for Utilization:* The solver assigns a low penalty (10 points/min) for being late, and a massive cost (5000 points) to deploy a new bus. This forces the system to cram more stops onto fewer buses, sacrificing punctuality.
*   The OR-Tools engine runs Parallel Cheapest Insertion and Guided Local Search algorithms to find the sequence of stops that results in the lowest mathematical score.

### Step 5: Evaluation (`optimizer.py`)
*   The generated sequence is passed to `evaluate_solution`.
*   This module calculates the final human-readable metrics: How many buses were used? What is the total penalty score?

### Step 6: Polyline Mapping (`main.py` & OpenRouteService)
*   Now that the logical order of stops is known (e.g., Bus 1 goes A -> C -> D), `main.py` iterates through the sequence.
*   It queries OpenRouteService (`directions` API) to get the exact turn-by-turn road curves (Polylines) between Stop A and Stop C.

### Step 7: Response to Client
*   The backend packages the final `schedule` list, the `polylines` dict (mapped by bus ID), and the `metrics`.
*   It returns an HTTP 200 JSON response to the React app.
*   The React app updates the Map UI and renders the Gantt chart timeline.

## 4. Key Algorithmic Concepts for Documentation

If you are writing algorithmic documentation, mention these core concepts:
1.  **Vehicle Routing Problem with Time Windows (VRPTW):** The foundational computer science problem this project solves.
2.  **Integer Linear Programming (ILP):** The mathematical framework used by OR-Tools under the hood to minimize the objective cost function.
3.  **Soft Boundaries vs Hard Boundaries:** Instead of failing if a bus cannot reach a stop on time (Hard Boundary), the system allows the bus to be late but applies a numerical penalty score (Soft Boundary) to gently push the solver toward better solutions.
4.  **Haversine Fallback:** If the external maps API goes offline, the system uses the Haversine formula (spherical geometry) to calculate point-to-point distances as a fallback so the app does not crash.
